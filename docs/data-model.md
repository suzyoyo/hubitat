# 好彼社區｜資料模型（假資料規劃）

從 Figma wireframe 三端（住戶、管委會、管理人員）的畫面反推而來。
狀態：**已確認（2026-10-06）**，依此分三批建立 `src/mocks/` 的假資料。

## 核心觀念：三端看的是同一批資料

同一筆資料，三端看到的內容和能做的事不同。例如：

```
住戶送出「通報」 ──→ 變成一筆「案件」 ──→ 管理人員受理、派廠商、標記完工
                                     └──→ 管委會追蹤、交辦、結案
                                     └──→ 住戶在「我的通報」看到進度
```

所以資料只建一份，由假 API 依角色決定回傳哪些欄位。

    - 待結案：「張管理員・9/25 完工驗收」（不寫「待結案」，徽章已經有了；待辦卡寫「張管理員已完工驗收，請結案」，因為是在叫你做）
    - 已結案：「大同電梯・9/12 結案」（沒有廠商就寫負責人：「張管理員・9/4 結案」）
    - 處理中的案件看不到負責人（一行放不下），點進案件詳情才看得到
  - **已完成**（2026-10-14，`getMyDoneTodos`）：最近 30 天我完成的事，新的在前。管委會：交辦給我、已完成的；我交辦出去、我確認完成的；我簽過的提案；我審核過的公告（通過或退回）；我負責、已結案的案件。管理人員：交辦給我、已完成的；我負責、已結案的案件。快到期文件、需補資料不算（它們是被處理掉，不是我做完的）

- **交接包**：從未結案案件、未執行決議、會議、合約、廠商彙整（另存一段「卸任者的話」）
- **緊急標示使用紀錄**：從標示為緊急的公告彙整
- **搜尋結果**：從案件、會議、文件、合約中搜尋

## 資料之間的關係

```
社區 ─┬─ 地點（棟別 → 地點）
      └─ 成員 ─┬─ 住戶
               ├─ 委員（主委、副主委、財務、修繕、監察）
               └─ 管理人員（總幹事、警衛）

案件 ──→ 通報人（成員）、地點、負責人（成員）、廠商、設備
  ├─ 附議（其他住戶「我也遇到了」）
  ├─ 處理進度紀錄
  └─ 施工日誌、廠商評分

交辦 ──→ 交辦人、交辦對象、關聯案件 或 關聯決議
提案 ──→ 發起人、選項（廠商報價）、各委員的簽核
公告 ──→ 發布者、審核者、影響地點、關聯案件、關聯設備
會議 ─┬─ 決議 ──→ 負責人、（交辦）
      └─ 住戶留言 ──→ 留言人、管委會回覆
廠商 ─┬─ 聯絡窗口
      ├─ 合約（多份，有歷次紀錄）
      └─ 負責的設備
設備 ──→ 地點、廠商；保養與維修紀錄 ──→ 關聯案件
```

## 各資料的主要欄位

### 1. 社區 `community.js`
- 基本資料：名稱（翠峰閣。「好彼社區」是 App 的名字，不是社區名稱）、地址、棟數、戶數、電話
- **地點清單**：範圍（A 棟、B 棟、C 棟、地下停車場、游泳池、中庭與戶外）→ 各範圍底下的地點（電梯／電梯口、樓梯間…）；可停用
- **問題分類**：漏水、設備故障、照明、噪音、水電、門窗鎖具…
- 內部聯絡（中控室、管理室、總幹事、主委）、鑰匙清單

### 2. 成員 `users.js`
- 姓名、棟別、戶號
- 身分：住戶／委員／管理人員。**一個人可以同時是住戶和委員**（畫面有「切換至管委會」）
- 委員職稱：主委、副主委、財務委員、修繕委員、監察委員
- 管理人員職稱：總幹事、警衛
- 屆次與任期（第 12 屆，2026/07～2027/06）

### 3. 案件 `cases.js`
- 案件編號（`CASE-20260925-003`）、標題、地點、分類
- 來源：住戶通報／管理人員登記／委員登記／巡查
- **公開或保密**：公共設施問題公開、涉及住戶行為保密
- 通報人、通報時間、問題描述、照片
- 狀態（見下方「狀態對照」）、處理期限（不存在案件上，用交辦的完成期限，假 API 算出 `deadline`；沒有交辦就是空字串、不算逾期，見 `case-flow.md` 4-1-2，2026-10-18）、預約到場時間（派廠商、改期時選填，`scheduledAt`）。**案件沒有「緊急」**（2026-10-16 拿掉 `isUrgent`：沒有畫面可以設，只有公告能標示緊急；之後要讓住戶通報時標緊急，再連同畫面一起加）
- 負責人、指派廠商、關聯設備
  - **誰可以受理、負責人是誰**（2026-10-13 和 suzy 定案）：管理人員、主委、副主委可以受理住戶通報；一般委員（財務、修繕、監察）不行。管理人員受理的，自己處理，負責人是他；主委或副主委受理的，再交辦給管理人員處理，負責人是主委或副主委。處理紀錄裡「受理」那一筆的 `actorId` 就是負責人
  - 主委、副主委受理後交辦給管理人員：**另開一筆交辦，用 `caseId` 連到這個案件**（2026-10-15 定案）。資料上案件的負責人不換人；畫面上的「負責人」是實際處理的人（交辦出去就是交辦對象，假 API 算出 `handlerLabel`）
- **主要流程的動作**（2026-10-15，規則和示範故事見 [case-flow.md](case-flow.md)，都只改記憶體）：主委、副主委、管理人員才能做（`canHandleCases`）
  - `acceptCase(id, userId, { category, equipmentId })` 受理：待受理 → 已受理，受理的人是負責人（處理期限不在這裡填，2026-10-18 拿掉）
  - `setCaseEquipment(id, userId, equipmentId)` 關聯設備：已受理、處理中可以選（或換）；設備先變待維修（維修中從廠商第一次到場那天起用日期算），換掉的那台變回正常使用中。畫面上受理是按了就受理，設備在案件詳情的「關聯設備」卡片選
  - `assignVendor(id, userId, { vendorId, vendorName, scheduledAt })` 派廠商（名冊裡的傳 `vendorId`，名冊裡沒有、自己打的傳 `vendorName`，先只記在案件上）：已受理、處理中 → 處理中；住戶看到「已安排廠商，預計 10/3 到場。」，不寫廠商名稱
  - `addCaseLog(id, userId, { text, residentText, scheduledAt })` 處理紀錄：給住戶看的另外寫一句（沒寫就不給看）；假 API 還能傳 `scheduledAt` 改期，但畫面上改期是在廠商卡片改預約時間
  - `updateCase(id, userId, { category, equipmentId, vendor, log })` 更新進度（2026-10-15）：上面三樣和 `category`（問題分類，2026-10-17 加）有填的一次做完，**只寫一筆**「更新進度」紀錄（一項一行，不寫是誰按的）。案件詳情底部的「更新進度」用這個
  - `completeCase(id, userId, { note, photos })` 完工驗收（已受理、處理中都可以；現場驗收，沒有「驗收不通過」）：管理人員按的 → 待結案，回到主委、副主委審核，連到的交辦一起回報完成（2026-10-15 改：管理人員自己受理的也一樣，原本是直接結案）；主委、副主委按的 → 直接結案
  - `closeCase(id, userId, { cost, note })` 結案（`note` 結案說明，寫進處理紀錄；2026-10-16 拿掉廠商評分）：待結案 → 已結案，**主委、副主委都能做**（2026-10-15 改，原本只有負責人）；連到的交辦一起確認完成
  - `returnCase(id, userId, reason)` 退回（2026-10-16）：待結案 → 處理中，主委、副主委都能做；連到的交辦一起退回，通知要再處理的人（`docs/case-flow.md` 4-6b）
  - 結案時有關聯設備的話，設備的維修紀錄多一筆（費用只記在這裡，只有委員填得了）。設備狀態跟著案件變：受理 → 待維修、**廠商第一次到場那天** → 維修中（用案件的 `firstVisitAt` 和今天算，不存在資料裡；已經來過、改期的還是維修中；待結案也算維修中）、結案 → 正常使用中
  - 結案後又壞了就開新案件，不把舊案件重新打開
- 附議的住戶
- 處理進度紀錄（時間、誰、做了什麼）
- 施工日誌、完工備註與照片、廠商評分
- **住戶新增通報時的地點**：只列出地點清單裡 `common: true` 的（住戶常會通報的），最後加一個「其他」讓住戶自己填（例如住戶家門口，涉及住戶行為的通報會用到）。機房、水塔這類地點沒有標 `common`，但管理端還是看得到
- **住戶新增與附議**：`createReport(userId, input)` 新增一筆通報（狀態是待受理、分類先歸「其他」）；`supportReport(id, userId)` 對別人公開、還沒結案的通報按「我也遇到了」。`getSimilarReports(areaId, place, userId)` 找同一個地點的相似通報，每筆有 `isMine`（我通報的）、`hasSupported`（我按過了）。都只改記憶體
- **代住戶登記通報**（2026-10-14）：管委會、管理人員用 `createRepair(userId, input, role)` 登記，來源是「委員登記」或「管理人員登記」，通報人是登記的人。可以選代哪一戶登記（`reporterUnit`：棟別＋戶號，例如 `{ building: 'A', unit: '6樓之3' }`），這時同一戶的住戶在「我的通報」都看得到這一筆（比對棟別＋戶號，不是比對帳號），通報有 `isOnBehalf: true` 和 `onBehalfLabel`（「管委會代為登記」或「管理人員代為登記」，給卡片、詳情頁顯示），只能看、不能修改。住戶看到的第一筆進度是「管委會（或管理人員）已登記，正在安排處理。」，不寫代哪一戶登記。管理端的通報人顯示成「李主委（代 A 棟 6樓之3）」
- **住戶修改**：`getReportById` 回傳的通報有 `canEdit`（是我自己通報的，而且還沒結案）。`updateReport(id, userId, changes)` 改補充說明和照片（地點、主旨不能改），有改到東西時處理紀錄多一筆「住戶補充」留存：管理端看到「陳先生（B 棟 8 樓）修改了補充說明、照片／影片」，住戶自己的處理進度看到「你修改了補充說明、照片／影片。」，下面用灰色小字列出改完的內容（紀錄的 `note`：補充說明的全文、照片的檔名；只改一項時不重複寫名稱）。這種紀錄不算管委會的回覆（「我的通報」卡片的最新回覆、進度條的「處理中」都不看它），但會更新「更新於」的時間。只改記憶體，重新整理網頁會變回原本的假資料
- **通報不能撤回**（2026-10-15 和 013 決定，`docs/case-flow.md` 第 7 節）：住戶和管理端都不能撤回，`withdrawReport`、`canWithdraw`、`cancelled` 狀態都拿掉了。不需要處理的通報由處理的人寫明原因結案
- **新增通報的標題**（2026-10-15，PR #56 討論）：`createReport`、`createRepair` 的 `title` 是地點＋通報問題（`${place}${subject}`，例如「1F 大廳門鎖壞了」），不放範圍：案件卡片的標籤就是範圍，放了會重複；但標籤沒有地點，標題不寫地點會看不出是哪裡。和設計稿「B2 車道排水孔堵塞」＋「地下停車場」的寫法一樣

**狀態對照**（同一筆案件，三端顯示的文字不同）

| 資料裡的值 | 管委會、管理人員看到 | 住戶看到 |
|---|---|---|
| `pending` | 待受理 | 已收到 |
| `accepted` | 處理中（2026-10-15 從「已受理」改，和 `in_progress` 顯示一樣） | 處理中 |
| `in_progress` | 處理中（2026-10-15 從「施工中」改名） | 處理中 |
| `to_verify` | 待結案（2026-10-15 從「待驗收」改名：管理人員已完工驗收，等主委或副主委結案） | 處理中 |
| `closed` | 已結案 | 已完成 |

### 4. 交辦 `tasks.js`
- 編號（`TASK-104`）、標題、內容（**選填**）、交辦人、交辦對象、完成期限（**選填**，2026-10-15 改；沒有是空字串）。必填的只有標題和交辦對象
- 狀態：進行中／待確認（對方已回報完成）／已完成／已撤回；「已逾期」由期限計算，沒有期限的不會逾期
- 沒有期限的交辦：`daysLeft` 是 `null`、列表排在最後、待辦的說明只寫「李主委交辦」、通知不寫期限、畫面上寫「未設定」
- 交辦對象：管委會新增交辦時只能選管理人員（2026-10-15 013 決定，畫面上的限制；假 API 沒有擋）
- 關聯案件或關聯決議（選填）
- 回報完成：附件、備註、回報時間
- **交辦人的動作**（2026-10-13 定案，`confirmTask`、`returnTask`、`withdrawTask`，只改記憶體）：只有交辦人能用
  - 確認完成：待確認時 → 已完成
  - 退回：待確認時 → 改回進行中，原因必填（`returnNote`）。可以給新的完成期限；原本的期限已經過了，畫面上要求一定要給，不然對方一被退回就逾期。退回後通知被交辦人，這件交辦會自動回到對方的待辦，提示是「已退回：原因」
  - 撤回：進行中（含已逾期）時 → 已撤回，原因必填（`withdrawReason`），通知被交辦人。待確認時不能撤回（對方已經做完，應該確認或退回）
  - 通知發到哪一端：被交辦人是管理人員就發管理人員端，是委員就發管委會端
- **新增交辦**（2026-10-15，`createTask(userId, { title, content, assigneeId, deadline, caseId })`）：只有主委、副主委（`canAssignTasks`）。有 `caseId` 的話，案件要還沒結案、同一件案件同時只能有一筆還沒完成的交辦，案件多一筆「交辦」紀錄（不給住戶看）。交辦後通知被交辦人
- **回報完成**（2026-10-15，`reportTask(id, userId, { note, files })`）：被交辦的人用，進行中 → 待確認，並清掉 `returnNote`。連到案件的交辦，在案件上按「完工驗收」時會自動回報

### 5. 提案 `proposals.js`
- 案號（`2026-088`）、標題、說明、發起人、簽核截止日
- 選項（廠商名稱、報價、附件）
- 各委員的簽核：同意／不同意（或選哪個選項）、意見、日期
- 狀態：簽核中／已通過／已否決

### 6. 公告 `announcements.js`
- 類型：施工／維護／活動／其他
- 標題、內容、日期時間（單日或多日）、影響範圍（可多選地點）或活動地點、主辦單位
- 是否緊急、推播對象
- 狀態：待補／待審核／已發布／已退回／已撤回
- 發布者、審核者（審核通過或退回的那一位）
- 退回：退回時間、退回原因（從固定的幾個原因選一個）
- **審核規則**：只有主委、副主委、管理人員能發布公告（財務、修繕、監察委員不能，2026-10-14 加）；主委、副主委發布的不用審核；管理人員發布的要經過主委或副主委審核；管理人員標示為緊急時不用審核，直接發布並同步通知管委會
- 撤回：撤回時間、撤回的人、撤回原因（選填）
- **修改、撤回**（2026-10-14 定案，`withdrawAnnouncement`、`restoreAnnouncement`，只改記憶體）：發布者本人，或是主委、副主委才能做；已結束的公告都不能
  - 撤回：已發布時 → 已撤回，住戶就看不到了。原因選填（和交辦不同：公告撤回常常很急，也沒有一個「一定要知道原因」的對象）
  - 復原：剛撤回後可以按 toast 上的「復原」→ 回到已發布。只有撤回的那個人能復原
  - 修改（`updateAnnouncement`）：已發布的改完立刻生效、不用重新審核，依推播設定通知住戶「公告已更新」。**管理人員改的，另外通知主委和副主委**「XX 修改了公告」（2026-10-14，PR #35）
  - **已撤回的不能修改、不能重新發布**（2026-10-14 決定）：撤回就結束了，要再發就發一則新的。剛撤回時可以按「復原」
  - 復原時，撤回時發給住戶的「公告已撤回」通知會收回
  - 撤回、發布、修改都會依推播設定（`push`）發通知給住戶
- **發布**（`createAnnouncement`，2026-10-14）：主委、副主委、管理人員才能發布（`canPublishAnnouncement`）；要審核的（管理人員發的、不緊急）→ 待審核，其他 → 直接發布並通知住戶。修改已發布的公告不用重新審核
  - `getAnnouncementById(id, role, userId)` 有傳 `userId` 時，會多 `canEdit`、`canWithdraw` 兩個欄位告訴畫面要放哪些按鈕
- 關聯案件、關聯設備（僅管委會可見）
- **已讀紀錄**（住戶端）：`getAnnouncements` 回傳的每則公告有 `isRead`；`markAnnouncementsRead(userId, ids)` 把幾則記成已讀。紀錄不存在資料檔裡，只記在記憶體，重新整理網頁會全部變回未讀
- 顯示用的欄位由假 API 附上：`typeLabel`（類型）、`scopeLabel`（影響範圍）、`relatedToMe`（是否與我有關）

### 7. 會議 `meetings.js`
- 類型：管委會例會／臨時會議／區分所有權人會議
- 名稱、日期、地點、出席狀況
- 狀態：待整理／待發布／已發布
- 檔案：會議紀錄、簽名簿與委託書（僅管委會可見）
- **決議**：標題、結果（通過／未通過／下次續審／報告事項）、表決票數、負責人、執行狀態（未執行／進行中／已完成）
  - 票數只有管委會看得到（「通過（同意 5、反對 0）」）；住戶、管理人員的議案列表只顯示結果「通過」（2026-10-14）
- **住戶版內容**：重點摘要、議案列表、全文記錄（已遮蔽個資）
- **住戶留言**：留言人、內容、時間、管委會回覆。管委會首頁的「住戶意見」就是彙整這些留言
  - **住戶新增留言**（2026-10-14，`createMeetingComment(meetingId, userId, text)`）：只有已發布的會議可以留言，內容最多 300 字（`MEETING_COMMENT_MAX`），不能是空的。留言會出現在管委會首頁的「住戶意見」。只改記憶體，重新整理網頁會變回原本的假資料

### 8. 廠商 `vendors.js`
- 名稱、統一編號、分類（電梯、消防、水電、清潔、保全、園藝）、處理項目
- 合作狀態：合作中／候選／停用
- 聯絡窗口（姓名、職稱、電話、LINE、是否列入緊急聯絡）
- 服務紀錄與統計由案件、設備紀錄計算

### 9. 合約 `contracts.js`
- 廠商、合約期間、金額、服務內容、承諾頻率、檔案、上傳者
- 狀態（合約內／即將到期／已到期／尚未生效）由日期計算
- 金額與合約全文**只有管委會看得到**

### 10. 設備 `equipment.js`
- 名稱、類別、地點、負責廠商、規格說明
- 安裝日期、保固到期日、保養週期、上次保養日（下次保養日由週期計算）
- 狀態：正常／待維修／維修中／已報廢；「保養逾期」「保養將到期」由日期計算
- **保養與維修紀錄**：日期、類型（例行保養／維修）、內容、廠商、費用（僅管委會可見）、關聯案件、照片

### 11. 文件 `documents.js`
- 法定文件：類型、名稱、到期日、是否公開給住戶
- 公開文件：財務報告、安全證明、會議通知
- 規約：版本、修訂日期、修訂說明、章節與條文

### 12. 時間軸 `timeline.js`
- 日期、類型（決議／工程／合約）、標題、說明

### 13. 通知 `notifications.js`
- 收件角色、標題、內容、時間、是否已讀、點了要去哪裡
- 住戶送出通報時（`createReport`），通知能受理的人：主委、副主委（管委會身分）、所有管理人員，通報的人自己也收（2026-10-15，見 `case-flow.md` 第 5 節）
- 頂部列的鈴鐺有未讀時加紅點（`AppShell` 每次換頁用 `getUnreadCount` 問一次）
- **設為已讀**（2026-10-15，只改記憶體）：`markNotificationRead(id)` 點進某一則時用，那一則的紅點消失；`markAllNotificationsRead(userId, role)` 按「全部已讀」時用，只改這個人、這個身分的通知。全部讀完，鈴鐺的紅點就消失。住戶端的通知頁也用這兩個

### 14. 留存 `quickSaves.js`
- 管委會和管理人員都可以使用
- 留存者（成員）、照片、名稱、備註、留存時間、是否已補齊、補齊後歸到哪個案件或設備
- **新增**（2026-10-18）：`addQuickSave(ownerId, { name, note, photos })`，「＋」選單的「快速留存」用。三樣都是選填，但至少要有一樣；新的一筆還沒補齊，馬上出現在留存者的待辦「需補資料」。只改記憶體
- **補齊**（2026-10-18）：`getQuickSaveById(id)` 給留存詳情頁；`linkQuickSaveToCase(id, userId, caseId)` 把留存歸到一件處理中的案件（只有留存的人自己能歸）：留存變成已補齊，案件的處理紀錄多一筆「附上留存」，備註放在 `note`、照片放在 `files`（給管理端看，住戶看不到）。設備不在留存這裡選，到案件詳情的「關聯設備」選

### 15. 邀請 `invites.js`
- 住戶端「加入管委會」流程用：主委給住戶一組邀請碼，住戶在「我的」頁輸入，確認後接受或婉拒
- 邀請碼（6 位數字）、邀請人、第幾屆、職稱（一般委員）、任期開始與結束日、邀請碼期限（建立後 72 小時）、住戶的回覆（接受／婉拒）、誰回覆的、回覆時間
- **一組邀請碼只能用一次**：接受或婉拒後就不能再用
- **接受後不用審核**，任期開始日才生效；在那之前身分還是住戶，「我的」頁顯示「待生效」（設計稿圖層裡留著「待審核」的舊文字，以畫面顯示的為準）
- 邀請碼的狀態（可以使用／查無此碼／已過期／已使用）由假 API 計算，提示文字在 `INVITE_STATUSES`
- 假 API：`getInviteByCode(code)` 查邀請，`status` 是 `valid` 才能用，其他狀態只回傳 `status` 和 `message`；`acceptInvite(code, userId)`、`declineInvite(code, userId)` 回覆邀請；`getMyAcceptedInvite(userId)` 拿我已經接受、還沒生效的邀請。都只改記憶體
- 假資料有三組邀請碼：`482913` 可以用、`135790` 已過期、`246810` 已使用（吳小姐接受了），邀請人都是李主委
- 管委會端「產生邀請碼」的畫面還沒有設計，所以還沒有建立邀請的假 API
- **示範住戶可以切換**：住戶端預設是李伯伯（主委），在 `/playground` 的「假資料」區可以切換成陳先生（一般住戶，`u-r01`），用來看「加入管委會」流程。選了誰記在瀏覽器的 `localStorage`（`hubitat-demo-resident`），只影響住戶端的 `getCurrentUser('resident')`；可以選的人在 `users.js` 的 `DEMO_RESIDENT_IDS`
