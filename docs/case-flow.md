為什麼要這份：我們決定先把「一個通報從頭走到尾」做完整（2026-10-15）。現在第 1 步（住戶通報）和住戶看進度都做好了，卡在中間的受理、交辦、處理、結案，三端都還沒有假 API。先把規則定下來，兩個人才能各自做畫面。

## 1. 示範故事（報告時照這條走）

| # | 誰 | 做什麼 | 案件狀態 | 設備狀態 |
|---|---|---|---|---|
| 1 | 住戶陳先生 | 通報「A 棟・電梯／電梯口・電梯異音」 | 待受理 | 正常使用中 |
| 2 | 李主委 | 受理，填完成日期、關聯設備「電梯（A 棟）」 | 已受理 | 待維修 |
| 3 | 李主委 | 交辦給張管理員：「聯繫大同電梯檢修 A 棟電梯異音」 | 已受理 | 待維修 |
| 4 | 張管理員 | 派廠商「大同電梯」，預約 10/3 14:00 到場 | 處理中 | 維修中 |
| 5 | 張管理員 | 10/3 當天沒修完，改約 10/5 再來（寫一筆處理紀錄） | 處理中 | 維修中 |
| 6 | 張管理員 | 10/5 修好、當場驗收，按「完工驗收」（同時回報交辦完成） | 待結案 | 維修中 |

| 9 | 住戶陳先生 | 「我的通報」變成已完成，進度條走到最後 | — | — |

另一條比較短的路：**管理人員自己受理**（第 2 步是張管理員），就沒有第 3 步的交辦；第 6 步完工驗收後**直接結案**，沒有第 7 步。

## 2. 狀態

| 資料裡的值 | 管委會、管理人員看到 | 住戶看到 | 改了什麼 |
|---|---|---|---|
| `pending` | 待受理 | 已收到 | |
| `accepted` | 已受理 | 處理中 | |
| `in_progress` | **處理中** | 處理中 | 原本叫「施工中」。聯繫廠商、等報價這種事不是施工 |
| `to_verify` | **待結案** | 處理中 | 原本叫「待驗收」。驗收是管理人員在現場做的，這一步是等負責人結案 |
| `closed` | 已結案 | 已完成 | |
| `cancelled` | 已取消 | 已撤回 | |

資料裡的值不改，只改顯示的文字（`CASE_STATUSES` 的 `label`）。

## 3. 交辦給管理人員：另開一筆交辦，用 `caseId` 連到案件

`data-model.md` 原本寫「主委或副主委受理後再交辦給管理人員，資料上要怎麼記還沒定」。**定案：另開一筆交辦**（2026-10-15）。

- 現成的確認、退回、撤回、待辦（「交辦給我的」「待我確認」）都能直接用
- 假資料本來就這樣寫：`TASK-092` 連到 `CASE-20260925-003`，張管理員在案件上寫處理紀錄
- 案件的負責人（`assigneeId`）還是受理的主委或副主委，不會換人
- 一件案件同時只能有一筆「進行中」的交辦。撤回或被退回後可以再交辦
- 被交辦的管理人員可以在這件案件上派廠商、寫處理紀錄、完工驗收（權限表本來就是管理人員都能做，這裡不另外限制）

## 4. 每一步的規則

「住戶看到」是處理紀錄的 `residentText`，住戶的通報詳情頁會自動顯示（沒寫就不給住戶看）。

### 4-1 受理 `acceptCase(id, userId, { deadline, category, equipmentId })`
- 誰：主委、副主委、管理人員（權限表）
- 什麼時候：待受理
- 做什麼：狀態 → 已受理；負責人 = 受理的人
  - **完成日期**（`deadline`，選填）：受理的人自己填，**不依「緊急」給預設值**。有填的話，過了日期還沒結案就算逾期（現成的逾期徽章、待辦到期日都看這個）
  - 問題分類（選填）：住戶通報時先歸「其他」，這時改成正確的
  - 關聯設備（選填）：有選的話，設備狀態跟著變，結案時進維修歷史
- 紀錄：「已受理」／「主委 李委員受理」（有填完成日期就加「，預計 10/8 前完成」）
- 住戶看到：「管委會已受理。」或「管理人員已受理。」（照現在假資料的寫法）
- 設備：正常使用中 → 待維修

### 4-2 交辦 `createTask(userId, { title, content, assigneeId, deadline, caseId })`
- 誰：主委、副主委（權限表）
- 做什麼：新增一筆進行中的交辦；有 `caseId` 的話，案件多一筆紀錄
- 紀錄：「交辦」／「主委 李委員交辦給 管理員 張管理員（TASK-105）」
- 住戶看到：不寫（住戶不需要知道內部分工）
- 被交辦的人：待辦裡出現在「交辦給我的」（現成的）
- 這個函式也給「會議決議交辦」用（那時 `caseId` 不傳）

### 4-3 派廠商 `assignVendor(id, userId, vendorId, scheduledAt)`
- 誰：主委、副主委、管理人員
- 什麼時候：已受理、處理中（可以換廠商）
- 做什麼：記下廠商；狀態 → 處理中
  - **預約到場時間**（`scheduledAt`，選填）：廠商敲定哪天來就填，例如 10/3 14:00
- 紀錄：「派廠商」／「張管理員指派 大同電梯，預約 10/3 14:00 到場」
- 住戶看到：「已安排廠商，預計 10/3 到場。」（沒填預約時間就是「已安排廠商處理。」；不寫廠商名稱）
- 設備：待維修 → 維修中

### 4-4 處理紀錄 `addCaseLog(id, userId, { text, residentText, scheduledAt })`
- 誰：主委、副主委、管理人員
- 什麼時候：還沒結案
- 紀錄：「處理紀錄」／`text`（管理端看的，可以寫廠商、報價這些細節）
- **住戶看到：另外寫一句 `residentText`**（選填，沒寫就不給住戶看）。管理端的寫法可能有廠商名稱、報價，所以不直接給住戶看
- **改期**：施工比預計久、要改天再來時，也是寫一筆處理紀錄，同時更新預約到場時間（`scheduledAt`）。例如管理端「大同電梯更換零件需調貨，改約 10/5 14:00」，住戶看到「廠商將於 10/5 再次到場處理。」

### 4-5 完工驗收 `completeCase(id, userId, { note, photos })`
- 誰：主委、副主委、管理人員
- 什麼時候：處理中
- 為什麼完工和驗收是同一步：廠商來處理時當場驗收，沒驗收完不能走，所以**沒有「驗收不通過」**
- 做什麼：記下完工紀錄（`completion`：時間、備註、照片）
  - **按的人就是案件負責人**（管理人員自己受理的）→ **直接結案**，接著做 4-7
  - **負責人是主委或副主委**（交辦出去的）→ 狀態 → 待結案；連到這件案件、交辦給這個人、進行中的交辦**一起回報完成**（回報備註就用完工備註），不用再到交辦頁按一次
- 紀錄：「完工驗收」／完工備註
- 住戶看到：「維修已完成，等待管委會結案。」（直接結案的就只顯示 4-6 的那一句）
- 待辦：負責人的待辦出現這件（主委是「我負責的案件」，現成的）

### 4-6 結案 `closeCase(id, userId, { cost, rating })`
- 誰：**案件負責人**（受理的那個人）。主委或副主委受理、交辦出去的，就是主委或副主委結案
- 什麼時候：待結案（管理人員自己受理的，在 4-5 完工驗收時就一起結案了）
- 做什麼：狀態 → 已結案、記下結案時間；有連到的交辦（待確認）一起確認完成
- 維修費用（選填）：只有委員填得了，管理人員沒有這一欄（管理人員看不到費用，權限表 2026-10-14）。費用記在設備的維修紀錄上，所以沒有關聯設備的案件不記費用
- 廠商評分（選填）：1～5 分＋評語
- 紀錄：「已結案」／「主委 李委員結案」
- 住戶看到：「已完成維修，感謝你的通報。」
- 設備：→ 正常使用中

### 4-7 變成維修歷史（結案時自動做）
- 案件有關聯設備的話，那台設備的紀錄多一筆：日期＝結案日、類型＝維修、內容＝案件標題、廠商、費用、`caseId`
- 沒有關聯設備的案件（例如住戶噪音）不進維修歷史，案件本身就是紀錄

### 4-8 結案後又發現問題
- 驗收通過後過幾天又壞了：**再開一件新的**（住戶再通報一次，或管理端登記），不把舊案件重新打開。舊案件的結案時間和維修紀錄已經寫好了，重新打開會亂掉
- 新案件可以連到上一件（之後再加欄位，示範先不做）

## 7. 討論紀錄（2026-10-15）

1. 交辦怎麼記 → 另開一筆交辦，用 `caseId` 連
2. 完成日期 → 受理的人可以填（選填），不依「緊急」給預設值
3. 預約到場時間 → 加（`scheduledAt`），派廠商、改期時填
4. 「施工中」→ 改叫「處理中」；「待驗收」→ 改叫「待結案」
5. 處理紀錄給住戶看的 → 另外寫一句
6. 驗收不通過 → 不做。現場驗收，沒驗收完廠商不能走；要改天再來就是改期；結案後又壞了就開新案件
7. 設備狀態 → 跟著案件變（待維修 → 維修中 → 正常使用中）
